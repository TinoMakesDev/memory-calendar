================================================================================
  Memory Calendar - Known Limitations
================================================================================

This document describes behaviors that look like bugs but are intentional,
cosmetic, or fixed at acceptable cost in other places. They are NOT patched.

Policy for future patches:
  Patch only if the change prevents:
  - data loss (file irrecoverably lost),
  - file corruption (file becomes unreadable),
  - application crash.
  Everything else goes into this file. No exceptions.

If you're reviewing the code and find a new issue, check this list first.
Most likely it's already documented with a rationale.

================================================================================
  A. INTENTIONAL DESIGN / UX DECISIONS
================================================================================

A1. Ctrl+Z cannot undo cut+paste done outside the app
  Scenario: cut inside app → paste via Windows Explorer → Ctrl+Z in app.
  Result: calendar restored, but file is not returned to original folder
  (destination path is unknown to the app — no filesystem watcher).
  Why: file system watchers on Windows are unreliable on network shares,
  limit ~10k handles per process, and don't reveal destination.
  Mitigation: status bar message "Ctrl+Z cannot undo external moves"
  shown when external move is detected.

A2. External drive disconnect → calendar entries stay as "missing"
  Scenario: user cut file from external drive → drive disconnects →
  cut-watch timer runs.
  Result: files NOT purged (3-tick confirmation, ~4.5s, plus parent-dir
  accessibility check before purge).
  Why: purging on transient disconnect would wipe calendar entries.
  Mitigation: Settings → "Find missing files" is a manual action with
  preview and confirmation; no auto-purge on open_gallery.

A3. Rotate in viewer does not create an undo entry
  Scenario: rotate image → Ctrl+Z.
  Result: previous file operation is undone, not the rotation.
  Why: rotation overwrites file in place via temp+os.replace; original
  bytes are gone (but orientation can be flipped back).
  Behavior matches most image editors (Lightroom, Photoshop quick rotate).
  Mitigation: none. Users who need to undo a rotate do it manually.

A4. Paste in "Months" / "Years" / "Duplicates" views is disabled
  Scenario: user opens Months view and presses Ctrl+V.
  Result: "Paste is only available in Gallery view" in status bar.
  Why: no single unambiguous target folder — gallery_context is "2024-03"
  or "2024", not a date key that maps to a folder.
  Behavior is a conscious restriction, not a bug.

A5. Paste-move between calendars drops cross-calendar membership
  Scenario: file is in Calendar A and Calendar B → cut in A, paste in A.
  Result: file moves to new path, old path purged from BOTH calendars,
  new path added to A only.
  Why: "move" = physical relocation = logical move; keeping a phantom
  entry in B pointing to a path that no longer exists is worse.
  If you need the file in both calendars: copy instead of cut.

A6. Paste-move drops event membership (move within app)
  Scenario: file belongs to event "Vacation 2024" → cut → paste
  somewhere else (still in same calendar).
  Result: file physically moved, entry added to calendar, but NOT
  re-attached to any events. _purge_path_everywhere(fp) removes
  old path from categories; new dest is not re-added.
  Why: "move" implies relocation; keeping the event slot pointing at a
  non-existent path is worse. Re-adding automatically would
  require tracking event membership through the paste pipeline.
  Workaround: use Copy instead of Cut. Or reassign event manually.
  Copy-paste is unaffected (source and event binding stay intact).

A7. Ctrl+E (assign event) works in Viewer, not in Gallery
  Why: Gallery already has "right-click → Assign event" and Ctrl+E is
  reserved for Viewer (where right-click menu is less discoverable).
  If needed: use context menu in Gallery.

A8. Cut + paste via OS on macOS/Linux behaves as copy, not move
  Scenario: cut a file in Memory Calendar, then paste it via Finder
  or Nautilus.
  Result: the external paste copies the file; the source remains on disk.
  Why: move intent is signalled with the Windows-only MIME type
  Preferred DropEffect (DROPEFFECT_MOVE). Finder/Nautilus ignore it.
  In-app paste still performs a real move via internal clipboard_action.
  Deferred until macOS/Linux hardware testing. NB-124.

A9. Events (categories) are global and not tied to a specific calendar
  Scenario: User has multiple calendars (e.g., "Phone", "Camera") and creates
  an event "Vacation 2024". User switches the active calendar.
  Result: The event "Vacation 2024" remains visible and keeps all its files,
  regardless of the currently selected calendar.
  Why: Events are designed as virtual albums that span the entire library.
  A user might have photos of the same trip scattered across different
  physical drives or folders. Tying events to a single calendar would
  require duplicate event creation and break the cross-library concept.
  This is a deliberate design choice for flexibility.

================================================================================
  B. LIMITATIONS OF UNDO/REDO MODEL
================================================================================

B1. Undo of copy-paste does not delete created copies
  Scenario: Ctrl+V (copy) → Ctrl+Z.
  Result: calendar state restored (no pasted entries), but copied files
  remain on disk as orphans.
  Why: redo cannot recreate deleted copies without the original source,
  so removing them on undo would make redo incomplete (or crash).
  Cost: orphan files accumulate; user sees them on next rescan.
  If needed: manually delete orphans from disk.

B2. Redo is explicitly skipped for paste-with-overwrite 
  Scenario: paste A over B (B → trash, A → dest) → Ctrl+Z → Ctrl+Y.
  Result: redo detects action["overwritten"], skips this redo step
  with a status-bar message:
  "Redo skipped: paste-with-overwrite cannot be replayed
  safely (disk state would desync). Use Ctrl+Z again, or
  paste again manually."
  The redo step is popped; disk and calendar stay consistent.
  Why: undo's bookkeeping for "overwritten" is not symmetric with redo;
  a silent replay would leave calendar pointing at "A" while disk
  has old "B". Correct replay would need to thread "which dest was
  created, which was trashed, in which order to release/replace"
  through history — error-prone in edge cases (occupied dest,
  trash auto-cleaned after 7d). Silent-wrong is worse than explicit
  refusal. See A-notes in patch log.
  Data safety: all versions preserved (trash + disk); Ctrl+Z still works;
  user can re-paste manually.
  Note on pure copy-paste (no overwrite): undo leaves the copy on disk
  (B1); redo just restores the calendar entry. That path is NOT
  skipped — it works correctly.

B3. Undo snapshots use copy.deepcopy — memory scales with library size
  Scale: for N files × undo_limit, peak memory ≈ N × undo_limit × ~200 bytes.
  For 100k files × 30 limit ≈ 600 MB peak.
  Why: deepcopy is simple and safe; delta-based undo is a large redesign.
  Mitigation: Settings → "Undo history depth" (1–200). Home users with
  < 20k files can leave it at 30. Library admins should
  reduce to 5–10.

B4. scan_finished pushes an undo state before validating target calendar
  HISTORICAL — fixed in (NB-17, see G19). Was: save_state_for_undo
  ran before target_name check; mid-scan deletion pushed a phantom
  undo step. Current behaviour: save_state_for_undo runs after the
  check. Kept as historical reference only.

  note: even if a similar race existed, the _scan_in_progress
  guard now blocks deleting/renaming the calendar being scanned —
  user cannot start those ops until the scan finishes.

B5. Undo after find_missing_files restores "phantom" entries
  Scenario: Find missing files → confirm cleanup → Ctrl+Z.
  Result: calendar entries pointing at non-existent paths are restored.
  Preview will be broken until next rescan or "Find missing
  files" again.
  Why: save_state_for_undo runs before purge (as designed). The
  snapshot correctly captures pre-purge state.
  This is a UX artifact of "undo restores data", not data loss —
  files are already gone from disk; only calendar entries come back.
  If needed: run Find missing files again, or rescan the folder.

B6. Undo with empty trash_path (file already gone) creates dead entry
  Scenario: move_to_trash returns (True, None) because file was missing
  pre-delete → undo restores snapshot with a path that
  doesn't exist on disk.
  Cosmetic — visible as "missing" until cleanup.

================================================================================
  C. CUT-WATCH / EXTERNAL-MOVE EDGE CASES
================================================================================

C1. _watch_cut_files requires 3 ticks (4.5s) of confirmed absence
  Scenario: cut → immediately paste via Explorer → close app within 4.5s.
  Result: file stays in calendar as a "ghost" until next manual refresh
  or next time _watch_cut_files runs.
  Why: 3-tick confirmation defends against AV/backup temporarily moving
  files out of a folder for a fraction of a second.
  Cost: 4.5s delay in the "fast close" scenario.
  Not patched: increasing ticks delays legitimate external-move
  detection; network shares with high latency are a
  documented trade-off.

C2. _watch_cut_files only runs when stack.currentIndex == 4 (Gallery)
  Scenario: cut → switch to Settings tab → paste in Explorer → back to
  Gallery.
  Result: on return to Gallery, timer ticks, purge runs within 1.5s.
  Why: to avoid running file I/O in background while user is in another
  tab. Behavior is "detects on next visit", not "monitors always".

C3. _cut_missing_streak entries for files that reappear are cleaned lazily
  Scenario: file briefly missing (streak 1–2) → reappears.
  Result: streak entry is dropped on next tick.

C4. Drag-Move from gallery to Explorer: partial move tracked, not full
  Scenario: select 3 files, drag to Explorer with Shift (Move), release.
  Result: moved files purged; remaining clipboard files stay in internal
  clipboard and cut-watch resumes.
  Why: drag.exec returns one action for the batch; we don't know which
  individual files succeeded on the OS side. The purge is based on
  os.path.exists check post-drop.

C5. _on_files_moved_externally under @_busy_guard dropped signal
  FIXED (NB-08). Previously: drag-move to Explorer while another
  long operation was in progress (_busy=True) → @_busy_guard silently
  returned → OS had moved files, calendar kept stale paths until manual
  rescan / Settings → Find missing files.
  Current behaviour: on _busy the handler defers via
  QTimer.singleShot(500, retry) and _busy flag is set only around the
  actual purge/rebuild work. `_on_files_moved_externally_impl` is
  idempotent (purge uses set; clipboard filter is idempotent), so
  double-call is safe. Retry log: "drag move: busy, deferring 500ms".

C6. _watch_cut_files in viewer did not flag gallery rebuild
  FIXED (NB-07). Previously: in viewer (stack==5), external move
  was detected, current file purged, `_on_viewer_back` entered gallery
  but `_gallery_needs_rebuild` stayed False → stale "phantom" card until
  user scrolled/resized.
  Current behaviour: `_gallery_needs_rebuild = True` is set before
  `_on_viewer_back`, so the non-dups rebuild path runs immediately.

================================================================================
  D. FILE SYSTEM / TRASH
================================================================================

D1. move_to_trash has bounded retry: 5 × 0.15s = 0.75s worst case
  Scenario: file locked by antivirus / another program.
  Result: after 5 failed attempts, deletion is reported as failed.
  Why: 10 retries × 0.15s = 1.5s per locked file was unacceptable on
  bulk operations (50 locked files = 75s freeze).

D2. Trash auto-clean retention is 7 days (based on entry time)
  FIXED: retention now uses the timestamp prefix embedded by
  move_to_trash (`f"mc_{ts}_{basename}"`), not the source file's mtime.
  Previously: shutil.move preserves mtime, so a photo taken 2 years ago
  and just deleted would be purged from trash on next app start
  (~2s after launch via check_auto_clean) — real data loss.

  v1.0 mc_-prefix note: trash entries created before the change
  (v0.x builds, filenames like `<ts>_<name>`) are NOT auto-cleaned.
  This is intentional and safe — old trash won't disappear on its
  own. If it grows large, clean it manually.

  Current behavior:
  - age = now − timestamp_parsed_from_filename (parsed from
  the leading <microseconds>_ prefix that move_to_trash adds)
  - files WITHOUT a prefix are LEFT ALONE. Previously,
  clean_trash fell back to st_mtime for unprefixed files —
  safe when trash_dir was hardcoded DATA_DIR/trash (..),
  but DANGEROUS after trash became user-configurable :
  a user pointing trash at a folder with e.g. "photo.jpg"
  would have that file silently deleted by retention.
  Now: no prefix → not ours → not touched. This is the honest
  way to keep "user-chosen trash folder" safe.
  - Retention period: config["trash_retention_days"] days
  (7..365, default 7; independent from cache retention.
  Range clamped both in Settings UI and in check_auto_clean —
  see D10 for the trash-folder feature.)

D3. Restore from trash can fail if target path is occupied
  Scenario: undo delete of A → someone created a new file at A's path.
  Result: restore_failed warning; A stays in trash.
  Why: silent overwrite on restore is data loss; refusing is safer.

D4. Sample-based hash for large photo files (> 6 MB)
  Scale: 2MB head + 2MB middle + 2MB tail = 6 MB read per file.
  Why for photos: photo bytes don't change in middle; two distinct
  photos with identical first/middle/last 2 MB would be identical
  everywhere.
  Videos: full hash — see D5.

D5. Videos > 6 MB always use full SHA-256
  Scale: 200 MB video = 200 MB read per dedup scan.
  Cost: dedup scan of large video library is slow.
  Why: sample-based hash false-positives real video pairs → wrong
  deletion. Data loss is worse than slow scan.

D6. Folders with "_" prefix or in SKIP_DIRS are skipped by scanner
  SKIP_DIRS: $recycle.bin, system volume information, .thumbnails,
  @eadir, __macosx, .cache, .local, node_modules.
  Plus: any folder whose name starts with "."

D7. restore_from_trash does not restore original mtime
  Scenario: delete file → Ctrl+Z.
  Result: file restored with shutil.move; mtime may differ from original.
  Why: preserving mtime would require os.utime after restore, and the
  "correct" value isn't stored anywhere.
  Impact: "Sort by date" may position file differently after restore.
  Not data loss — file content is intact.

D8. _cleanup_backups sorts lexicographically, not by mtime
  FIXED (NB-16). Previously: sorted(glob) is string-
  comparison — "…_1.json" sorts AFTER "….json", so collision-
  suffixed backups survived longer than their siblings.
  Current behaviour: sort by st_mtime via _safe_backup_mtime
  helper (tolerates concurrent unlink race). BACKUP_KEEP still
  enforced.

D10. Trash folder is configurable 
  Settings → Data safety → "Trash (deleted files)" allows picking
  any folder as the trash destination, plus a retention spinner
  (7..365 days). Defaults: DATA_DIR/trash, 7 days.
  - set_trash_dir rejects empty, ".", "..", root ("/",
  "C:\\"), and non-absolute paths — otherwise clean_trash
  would iterdir over the whole drive / CWD, and
  move_to_trash would fail on every file (PermissionError).
  - clean_trash only removes files matching the trash
  prefix (^mc_\d+_). Files without prefix in the trash folder are
  untouched — user can point trash at a folder with other data
  without fear (see D2 for full rationale).
  - changing trash folder prompts a warning dialog
  explaining that auto-cleanup will run inside this folder
  (only prefixed files removed), and recommends a dedicated
  empty folder. Cancel rolls back the label.
  - Validation on change: set_trash_dir calls mkdir; on failure
  (bad path / permission / disk) TRASH_DIR is left unchanged and
  the UI label is rolled back to the real path.
  - Retention is independent from cache retention (was previously
  tied to auto_clean_days; splits them).
  - Existing files in the OLD trash folder are NOT migrated when
  the path changes. Undo still works because each action records
  its own trash_path; old trash drains under its own retention
  at the next launch where it is still the active trash.
  - Hint in Settings warns: do NOT point trash inside your photo
  library — trashed files may be re-scanned as originals.
  Not a limitation — a documented feature. Kept here so reviewers
  understand the trash-path variable and undo invariants.

D9. force_clear_cache runs synchronously on UI thread
  Scenario: Settings → "Clear cache now" with 10k+ files.
  Result: window freezes ~50–200ms (HDD).
  Not patched: not data-loss.
  Tracked as NB-20.

================================================================================
  E. VIDEO / EXIF / IMAGE FORMATS
================================================================================

E1. HEIC rotation requires pillow-heif installed
  Result: file untouched, user sees "HEIC: support unavailable".
  Why: silent conversion to JPEG-with-.heic-extension corrupts file.

E2. HEIC can fail to load in fullscreen viewer without Qt HEIF plugin
  Same as E1 mitigation (PIL fallback).

E3. EXIF sub-IFD write may lose DateTimeOriginal on Pillow < 9.2
  Mitigation: warning logged. Update Pillow.

E4. get_exif_date does not parse subseconds or timezone offsets
  Format lost: "2024:01:01 12:00:00+03:00" or "2024:01:01 12:00:00.123"
  Cosmetic — rare format.

E5. HEIC thumbnails via PIL only; not via Qt's QImageReader
  Cost: PIL path is slower than Qt native on some systems.

E6. Video preview uses first frame (~10% in); no scrubbing
  If video can't be opened: no thumbnail.

E8. Pillow 9.0 cannot render thumbnails (Resampling added in 9.1)
  Impact:  Image.Resampling.LANCZOS was introduced in Pillow
  9.1; on 9.0 AttributeError is caught by
  ThumbnailLoader except handler -> "..." or
  "No preview" placeholder forever. No crash; no
  data impact; only missing previews.
  Why:  Hard requirement now documented in README (Pillow
  >= 9.1). Fix would be a runtime fallback:
  try: LANCZOS = Image.Resampling.LANCZOS except
  AttributeError: LANCZOS = Image.LANCZOS. Not
  worth the extra branch for a documented minimum.
  Not a bug. Documented requirement.

E7. Transparent PNG/WebP thumbnails were permanently blank ("...")
  FIXED (NB-04). Previously: ThumbnailLoader single-file path
  called `img.tobytes("raw", "RGB")` on the fitted image without
  `.convert("RGB")`. For non-RGB modes (RGBA, LA, P), Pillow raised
  ValueError → caught by except Exception → "..." placeholder forever
  (until re-open_gallery after a rotate).
  Current behaviour: fitted image is `.convert("RGB")` before
  tobytes — same as generate_quad_thumbnail and ImageViewer already did.

================================================================================
  F. UI / UX
================================================================================

F1. Ctrl+Z/Ctrl+Y in Manager/Settings/Help tabs is ignored
  Why: file undo only makes sense in Calendar/Gallery/Viewer.

F2. Ctrl+Z on QSpinBox/QComboBox is ignored (not forwarded)
  Why: spinbox "undo" is just typing history; combo has no undo.

F3. Paste into empty event shows "Cannot paste into empty event"
  Why: no target folder exists yet for this event.

F4. refresh_all_views after find_missing_files exits Duplicates view
  Why: last_dups invalidated by purge; re-entering Duplicates requires
  rescan.

F5. Event cards show only events with ≥ 1 existing file
  Why: filter avoids rendering "5 files" badge on a card that opens
  to an empty gallery.

F6. Empty calendar + Duplicates view → falls back to Days
  No data issue.

F7. Theme change: social buttons keep their gradient
  Why: inline gradient QSS not touched by apply_styles. Cosmetic.

F8. "Export language template" exports template, not current language
  Behavior is intentional (template for translators).

F9. Status bar counters may be approximate
  Cosmetic — behavior of underlying operation is correct.

F10. Ctrl+A in GalleryWidget uses WindowShortcut context
  FIXED (NB-05). Previously: focus in Settings or Help tab,
  Ctrl+A reached GalleryWidget._select_all via WindowShortcut
  and silently selected items in the hidden gallery list.
  Current behaviour: _select_all returns early if
  GalleryWidget.isVisible is False — Qt returns False for
  non-active QStackedWidget pages, so Ctrl+A in Settings/Help no
  longer propagates. In Days/Months/Years/Events/Duplicates
  (gallery is the active page) Ctrl+A still works as before.

F11. change_view_mode: btn_rescan_dups stays visible after fallback
  FIXED (NB-14). Previously: Duplicates view → calendar
  becomes empty → auto-fallback to Days; currentIndexChanged was
  blocked so change_view_mode(0) never ran and the "Rescan" button
  stayed visible in Days until the next user click.
  Current behaviour: the fallback branch calls
  self.btn_rescan_dups.hide explicitly.

F12. _rebuild_translatable_widgets: idx == -1 loses widget position
  FIXED (NB-06). Previously: if settings_view was already
  detached from the stack (double-fired language_changed, or
  deleteLater race), idx == -1 and the newly created widget was
  orphaned — Settings tab showed empty/wrong widget.
  Current behaviour: if idx < 0, insert at stack.count and
  log a warning. Same for manager_view. Happy path unchanged.

F13. paste_files overwrite: window where dest is absent
  Scenario: overwrite confirmed → move_to_trash(dest) succeeds →
  shutil.copy2 fails (disk full, I/O error).
  Result: dest is in trash, new file not created. User sees "file
  missing" until Ctrl+Z (restores from trash).
  Why: trash-before-write is required for safe undo.
  Data is preserved in trash. Not data-loss.

F14. on_gallery_delete_dups used defaultButton=Yes for multi-file
  FIXED (NB-02). Previously: default Button was Yes regardless
  of N. Users pressing Enter without reading could mass-move all
  duplicates to trash; if user performed ≥ undo_limit actions before
  Ctrl+Z, undo would roll off and recovery required manual trash dig
  (auto-clean 7 days).
  Current behaviour: default Yes for N==1 (trivial undo), No for
  N>1 — same rule as delete_selected_files .

F15. Ctrl+Z from modal non-text widget triggers file undo
  FIXED (NB-15). Previously: AssignEventDialog / QInputDialog
  with focus on OK button (not in QLineEdit) → Ctrl+Z reached
  MainWindow.undo. File undo executed while dialog was open.
  Current behaviour: undo/redo check QApplication.
  activeModalWidget after text-widget forwarding and spin/combo
  ignore; if a modal is open (and not self), return. Text-widget
  Ctrl+Z inside the modal still forwards to local undo.

F16. Modal dialog opened during _busy re-enters undo/redo timers
  Note: this is the opposite of F15 — while a modal dialog is up,
  _busy=True (e.g., inside delete_selected_files), and Ctrl+Z is
  blocked by _busy_guard. Net effect: no data corruption.
  Documented for reviewers.

F18. CalendarManagerWidget.list_events showed white box in dark theme
  FIXED. Previously: list_events (QListWidget) had no
  explicit setStyleSheet. In Fusion dark theme, QListWidget falls
  back to default palette Base color (white, since setPalette is
  never called) — visible as a stark white box inside the grey
  Manage → Events panel. Other QListWidgets (Settings priority
  list, GalleryListWidget) set their own style; this one was
  missed. Current behaviour: explicit QListWidget style
  in CalendarManagerWidget.update_theme, matching SettingsWidget
  for consistency. Cosmetic — no data impact.

F19. find_missing_files had no progress feedback
  FIXED. Previously: iterating cal_data × os.path.exists
  on a 10k+ library (especially HDD or network drive) froze the
  window for several seconds with no visible activity — users
  assumed the app had hung. Current behaviour: pre-count
  total entries (O(lists), no I/O), show determinate progress
  bar ("N / M"), call _process_ui every 200 files to let the
  bar paint. Determinate, cancellable by Finish button
  (project rule: no user-initiated cancel needed). Cosmetic —
  no data impact.

F17. Safe media add  — two-level scan protection
  While a folder scan is running (self._scan_in_progress == True),
  two levels of protection apply:
  LEVEL 1 (always):
  Destructive operations are BLOCKED with a status-bar message
  "Please wait — scan in progress" (2s). Blocked ops:
  delete_selected_files, paste_files, undo, redo,
  on_gallery_delete_dups, find_missing_files,
  restore_from_backup, _on_files_moved_externally,
  clear_calendar, delete_calendar, rename_calendar,
  load_external_calendar, import_folder, change_view_mode(4)
  (entry to Duplicates view is also blocked — parallel
  dup-scan would cause I/O thrash + unreliable file set).
  Navigation, gallery, viewer, viewer ←/→, zoom, settings,
  copy/cut (clipboard only — paste is blocked), event
  create/rename/delete, assign_category, remove_from_event —
  all allowed. None of them set _busy or touch _scanned_files,
  so no race with the scan merge.
  LEVEL 2 (opt-in, default ON):
  Settings → Data safety → "Safe media add: block UI above [N]
  media file(s)". Default ON, threshold 50 (range 10..10000).
  When total > threshold, a modal ScanProgressDialog opens:
  "Adding media files / Please wait while media files are
  being added to the calendar…" with a progress bar and
  Cancel button. The whole MainWindow is locked while open.
  Cancel / Esc / ✕ all abort the scan (treated as scan
  cancellation, NOT as app close); the dialog closes
  automatically after merge finishes.
  Esc now genuinely cancels — previously QDialog::reject
  hid the dialog without emitting cancel_requested, leaving
  the scan running with no UI. Also: ScanProgressDialog opens
  ONLY for main scan (ScannerThread) — never for
  DuplicateScanThread. update_progress is shared between both
  threads; without the _scan_in_progress guard dup-scan would
  open the modal dialog and Cancel would not stop it.
  Cross-effect: NB-26 (QTimer-drop race between scan_finished
  and closeEvent) is architecturally eliminated — _busy cannot
  become True during a scan → scan_finished never defers →
  QTimer.singleShot(200) is never scheduled during scan →
  no QTimer to drop. See I33.

  Known interaction:
  - If the checkbox is OFF, LEVEL 2 is skipped — LEVEL 1 still
  applies (destructive ops remain blocked during scan).
  - If total == 0 (empty folder) or total <= threshold, no
  modal dialog appears; only the status-bar progress indicator
  (same as pre-behaviour), but LEVEL 1 blocking is active.
  - Duplicates view cannot be entered during a main-scan; the
  combo stays on the current mode with a status message.
  - This is a behaviour change, not a limitation — documented
  here so reviewers understand why destructive ops are
  temporarily no-op during scans.

================================================================================
  G. TECHNICAL / INFRASTRUCTURE
================================================================================

G1. _process_ui uses ExcludeUserInputEvents, not queued-signal exclusion
  Why: full processEvents block would freeze progress bar; guard is at
  scan_finished/on_duplicates_found via _busy check + 200ms defer.

G2. cv2.VideoCapture may hang on broken/network files
  Mitigation: daemon thread + 5s join timeout; semaphore (4 concurrent)
  prevents full UI freeze; leaked semaphore on hang means
  video previews stop for that session.
  Requires subprocess-based isolation to fully fix (work item).

G3. QThread.terminate in closeEvent after 15s timeout
  Why: better than QThread-UB crash on exit. Last resort.

G4. First save with `_last_saved_count == -1` calls _count_files_in_json
  Cosmetic — one extra disk read on very first run.

G5. _save_timer debounce 500ms
  Scenario: hard kill -9 / power loss within 500ms of last action.
  Result: last 500ms of changes lost (but closeEvent flushes before exit).

G6. _purge_paths_bulk / _purge_specific_paths have no try/except
  Why: categories guaranteed to be list after _sanitize_calendars.

G7. Two purge helpers (_purge_paths_bulk, _purge_specific_paths) coexist

H1. "Video semaphore busy, skipping: <path>" — 4 concurrent previews

H2. "Video frame extraction timed out after 5.0s" — file couldn't be

H9. "qt.gui.imageio.jpeg: Corrupt JPEG data: N extraneous bytes"
  in terminal (or stderr) when viewing/thumbnail-loading certain
  JPG files.
  Cause:  Qt's built-in JPEG decoder (not our code) reports
  these warnings when a JPEG has extraneous bytes
  after the EOI marker (0xd9). Common for photos from
  some cameras/editors. The image itself decodes fine.
  Qt logs to stderr at INFO level; message format is
  "qt.gui.imageio.jpeg: Corrupt JPEG data: ...".
  Impact:  Cosmetic. Image renders correctly. If QImageReader
  fails entirely (rare), our PIL fallback in
  ImageViewer.update_view handles the file.
  Not a bug. Cosmetic Qt-side log noise.

H8. "--- Logging error ---" + OSError [WinError 1] in terminal while
  scrolling a video gallery (dev-mode only).
  Scenario: 4 concurrent video-frame workers. Each enters
  with suppress_stderr (refcounted). While ANY
  worker is inside the suppression window, fd 2 = devnull.
  If another worker / parent thread calls logger.info
  during that window, StreamHandler writes to a devnull-
  backed fd, which on Windows raises ERROR_INVALID_FUNCTION
  inside logging.emit.
  Impact:  File log (app.log) works; every line lands there. Only
  the terminal StreamHandler emits the "--- Logging error ---"
  traceback. PyInstaller --noconsole build has
  sys.stderr=None → StreamHandler not created → error
  absent entirely.
  Why:  refcounting was correct for the suppression itself;
  the noise is a side-effect of having BOTH suppressed
  and un-suppressed writers to the same fd. Full fix
  would require per-thread stderr redirection (OS-level
  per-thread handles, not portable on Windows) or moving
  StreamHandler off fd 2 — large redesign, zero user
  impact.
  Not a bug. Cosmetic dev-mode noise. See G2, H1, H2.

================================================================================
  J. CROSS-PLATFORM (BETA)
================================================================================

J1. macOS and Linux are BETA
  The application was built with cross-platform frameworks (PySide6, Pillow,
  OpenCV), but the maintainer only has access to Windows for testing.
  macOS and Linux builds contain platform-specific logic (e.g., Apple fonts,
  dbus calls, Backspace mapping) but are not end-to-end tested.
  Do not use these builds for irreplaceable data without a backup.

J2. File creation date (PRIO_CTIME) is unavailable on Linux
  Linux filesystems (ext4, btrfs) do not expose file creation time via
  standard Python `os.stat` (st_birthtime is missing, st_ctime is metadata
  change time). The app automatically hides PRIO_CTIME in Settings and
  filters it out of the priority list on Linux to prevent 0-file scans.

J3. "Show in folder" relies on dbus on Linux
  We use `dbus-send` to ask the system file manager (Nautilus, Dolphin) to
  highlight the selected file. If the dbus call fails (e.g., no desktop
  portal, SSH session), it falls back to `xdg-open` which opens the parent
  folder but does not highlight the file.

J4. Native font detection
  On Windows, Segoe UI is used. On macOS, `.AppleSystemUIFont` is used.
  On Linux, it falls back to the system default sans-serif (usually DejaVu
  Sans or Noto Sans) defined by the OS Qt theme.

================================================================================
  K. HOTKEY EDITOR (+)
================================================================================

K1. Configuration uses PortableText
  Hotkeys are saved in config.json as "Ctrl+E", "Shift+Alt+X", etc.
  Never "Meta+" or "Cmd+". Qt translates "Ctrl" to the Command key
  on macOS automatically (`QKeySequence.NativeText`).

K2. Conflict resolution
  If you assign a shortcut that is already used by another action, a
  dialog asks for confirmation. If you accept, BOTH actions will share
  the shortcut. Qt will trigger them based on the currently focused widget
  (or trigger both if both are global, which is not recommended).

K3. Empty field = Disabled
  Clearing a QKeySequenceEdit field (or clicking the red ✕ button) sets
  the key to an empty string. This explicitly disables the keyboard shortcut
  for that action, though the menu item or button will still work.

K4. Profile vs. Explicit Overrides
  Switching the "Platform profile" (Auto/Windows/macOS/Linux) changes the
  defaults for actions you haven't explicitly overridden. If you manually
  set "Undo" to "Ctrl+Alt+Z" on Windows, switching the profile to macOS
  will NOT change your Undo override (it stays Ctrl+Alt+Z).

K5. macOS Backspace default
  The default "Delete" shortcut on macOS is Backspace, not Del. This is
  applied automatically when the macOS profile is selected. On Windows and
  Linux, it remains Del.
